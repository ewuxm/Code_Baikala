## О проекте

«Код Байкала AI» --- прототип интеллектуального ассистента, который
позволяет задавать вопросы к данным университета обычным человеческим
языком, не требуя от пользователя знания SQL.

Основной сценарий:

``` text
Вопрос пользователя
       ↓
Проверка роли и вопроса
       ↓
Получение схемы PostgreSQL
       ↓
YandexGPT → генерация SQL
       ↓
Очистка и валидация SQL
       ↓
Whitelist + только SELECT
       ↓
LIMIT + read-only transaction + statement_timeout
       ↓
PostgreSQL
       ↓
Результат БД
       ↓
Формирование понятного ответа
       ↓
Ответ + SQL + таблица результата
```

Проект разработан под базовый кейс хакатона: связка **«Вопрос → LLM →
SQL → Проверка → Выполнение → Корректный ответ»** с фокусом на
корректность, безопасность и стабильность.

------------------------------------------------------------------------

## Зачем это нужно

Университет располагает большим объёмом данных: студенты, преподаватели,
учебные планы, расписание, приёмная кампания, отчётность и статистика.
Эти данные хранятся в PostgreSQL, но традиционный доступ к ним требует
знания SQL.

Ассистент решает эту проблему через простой интерфейс:

-   пользователь пишет вопрос на естественном языке;
-   система учитывает выбранную роль;
-   YandexGPT формирует SQL на основе реальной схемы БД;
-   запрос проходит отдельную проверку безопасности;
-   PostgreSQL выполняет его в read-only транзакции;
-   пользователь получает понятный ответ и при необходимости может
    посмотреть SQL и результат.

## Возможности

### Natural Language → SQL

Пользователь не пишет SQL самостоятельно. Модель получает:

-   вопрос пользователя;
-   описание разрешённых relations;
-   структуру таблиц и views;
-   внешние ключи;
-   правила конкретной роли.

После этого генерируется один PostgreSQL `SELECT`.

### Ролевая модель

Поддерживаются три роли:

  -----------------------------------------------------------------------
  Роль                                Доступ
  ----------------------------------- -----------------------------------
  **Абитуриент**                      факультеты, направления,
                                      поступление и открытая статистика

  **Студент**                         открытые данные + учебная
                                      информация, расписание, оценки,
                                      академическая статистика, сведения
                                      о преподавателях

  **Преподаватель**                   все relations, разрешённые
                                      приложением, включая учебные и
                                      статистические данные
  -----------------------------------------------------------------------

Важно: в текущем прототипе роль **выбирается пользователем без
аутентификации**. Это механизм ограничения доступа, а не подтверждение
личности. Для production-системы роль необходимо связывать с реальным
аккаунтом/SSO/LDAP.

### Защита SQL

Перед выполнением запрос проверяется:

-   запрос должен начинаться с `SELECT`;
-   запрещены несколько SQL-операторов;
-   запрещены `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`,
    `CREATE`, `GRANT`, `REVOKE`, `COPY`, `CALL`, `DO`, `VACUUM`,
    `ANALYZE`, `EXECUTE`, `PREPARE` и другие опасные конструкции;
-   запрещён доступ к системным схемам PostgreSQL;
-   `FROM`/`JOIN` проверяются по whitelist;
-   для ролей с ограниченным доступом запрещён вывод персональных данных
    студентов;
-   `SELECT * FROM students` запрещён для `applicant` и `student`.

### Контроль объёма данных

Если пользователь не указал `LIMIT`, приложение добавляет:

``` sql
LIMIT 100
```

Для передачи результата в LLM сериализуется не более 50 строк.

Это позволяет не отправлять большие массивы данных в модель и
ограничивать объём ответа.

### Таймаут PostgreSQL

Каждый запрос выполняется в транзакции:

``` sql
SET TRANSACTION READ ONLY;
SET LOCAL statement_timeout = '5000ms';
```

То есть приложение не должно изменять данные БД, а слишком долгий запрос
автоматически останавливается.

### Исправление SQL

Если PostgreSQL возвращает ошибку, приложение может передать ошибку и
предыдущий SQL обратно в YandexGPT для исправления.

Максимум --- **2 дополнительные попытки**.

Каждый исправленный SQL снова проходит валидацию перед выполнением.

### Корректный ответ

Для некоторых важных количественных сценариев ответ формируется
детерминированно из результата БД. Это уменьшает риск того, что LLM
изменит число или неверно интерпретирует результат.

Для остальных запросов YandexGPT формирует короткий русскоязычный ответ,
используя только данные из результата БД.

### Логирование

Запросы записываются в таблицу `query_logs`.

Сохраняются:

-   пользовательский вопрос;
-   роль;
-   сгенерированный SQL;
-   выполненный SQL;
-   время ответа;
-   количество строк;
-   статус;
-   сообщение об ошибке.

# Как проходит обработка вопроса

### Шаг 1. Проверка роли

Сервер проверяет подписанную cookie.

Если роль отсутствует или подпись некорректна, запрос не выполняется.

### Шаг 2. Проверка вопроса

Проверяется:

-   наличие вопроса;
-   максимальная длина --- 1000 символов;
-   соответствие базовым ограничениям выбранной роли.

### Шаг 3. Получение схемы БД

Приложение читает:

-   таблицы/views из whitelist;
-   колонки;
-   типы данных;
-   внешние ключи.

Схема кэшируется после первого получения.

### Шаг 4. Генерация SQL

YandexGPT получает вопрос, схему и описание роли.

Модель должна вернуть **один SELECT**.

### Шаг 5. Нормализация SQL

Перед валидацией:

-   удаляются markdown-обёртки;
-   удаляются ненужные SQL-комментарии;
-   нормализуются некоторые значения сущностей, например названия
    факультетов.

### Шаг 6. Валидация

Проверяется:

``` text
SELECT?
↓
один оператор?
↓
нет запрещённых конструкций?
↓
нет системных схем?
↓
relations входят в whitelist?
↓
нет запрещённых персональных полей?
```

Только после успешной проверки SQL может попасть в PostgreSQL.

### Шаг 7. Ограничение результата

Если в SQL нет `LIMIT`, приложение добавляет:

``` sql
LIMIT 100
```

### Шаг 8. Выполнение

Запрос выполняется в:

``` text
READ ONLY transaction
```

с:

``` text
statement_timeout = 5000 ms
```

### Шаг 9. Repair loop

При ошибке PostgreSQL приложение может запросить у YandexGPT исправление
SQL.

Максимум:

``` text
2 попытки исправления
```

Каждый новый SQL снова валидируется.

### Шаг 10. Ответ пользователю

Пользователь получает:

-   текстовый ответ;
-   SQL;
-   результат PostgreSQL в таблице;
-   время обработки.

# Что пока не является частью MVP

Памятка хакатона отдельно выделяет дополнительные возможности, которые
могут дать бонусные баллы.

### Работа с большими данными

В текущей реализации уже есть:

-   автоматический `LIMIT`;
-   ограничение количества строк;
-   ограничение объёма данных, передаваемых LLM.

Но отдельно не реализованы все дополнительные элементы из задания:

-   анализ потенциального объёма выборки;
-   интерактивное предупреждение о широком запросе;
-   предложение фильтров;
-   полноценная пагинация.

### Explainable AI

Текущий интерфейс показывает SQL и результат БД, но отдельный
структурированный `explanation block` с:

-   использованными таблицами;
-   JOIN;
-   фильтрами;
-   агрегатами;
-   добавленными ограничениями

не является отдельным реализованным модулем.

Важно: explainability должна показывать **структуру выполненного
запроса**, а не внутреннюю цепочку рассуждений модели.

# Архитектурные особенности

## Асинхронность

Основная обработка построена на `asyncio`.

Подключение к PostgreSQL выполняется через асинхронный пул `asyncpg`.

HTTP-сервер также использует асинхронный API Python.

Вызов YandexGPT через библиотеку `requests` переносится в отдельный
поток с помощью:

``` python
await asyncio.to_thread(...)
```

чтобы синхронный HTTP-вызов не блокировал основной event loop.

## Connection pool

PostgreSQL pool создаётся с параметрами:

``` text
min_size = 1
max_size = 10
command_timeout = 15 секунд
```

## Кэширование схемы

Схема разрешённых relations загружается из PostgreSQL и сохраняется в
`SCHEMA_CACHE`.

Это позволяет не запрашивать структуру БД заново для каждого вопроса.

# Безопасность

Безопасность проекта строится не только на prompt engineering.

Используется несколько независимых уровней:

``` text
             ┌───────────────────────┐
             │  Роль пользователя    │
             └───────────┬───────────┘
                         ↓
             ┌───────────────────────┐
             │ Проверка вопроса      │
             └───────────┬───────────┘
                         ↓
             ┌───────────────────────┐
             │ YandexGPT → SQL       │
             └───────────┬───────────┘
                         ↓
             ┌───────────────────────┐
             │ SQL validation        │
             │ SELECT / whitelist    │
             │ forbidden patterns    │
             └───────────┬───────────┘
                         ↓
             ┌───────────────────────┐
             │ READ ONLY transaction │
             │ + timeout             │
             └───────────┬───────────┘
                         ↓
                    PostgreSQL
```

Это принципиально важно: LLM не получает право самостоятельно решать,
какой SQL безопасно выполнять.

# Ограничения текущего прототипа

Перед production-использованием необходимо усилить несколько
компонентов.

### 1. Аутентификация

Сейчас пользователь самостоятельно выбирает роль.

Для production:

``` text
SSO / OAuth / LDAP / корпоративная IAM
        ↓
реальный user_id
        ↓
роль из доверенного источника
```

### 2. SQL parser

Текущая защита SQL основана на нормализации и регулярных выражениях.

Для production желательно добавить полноценный SQL parser /
AST-анализатор.

### 3. Отдельный DB user

Приложению следует выдавать отдельного PostgreSQL-пользователя с
минимально необходимыми правами.

### 4. Секреты

Все API keys и пароли должны храниться только в secret manager /
environment variables.

### 5. HTTPS

Для публичного размещения необходим TLS и reverse proxy.

# GitHub: как опубликовать проект

Перед первым commit:

``` bash
git init
git branch -M main
git add .
git status
```

Проверьте, что в `git status` **нет**:

``` text
.env
API keys
паролей PostgreSQL
секретных JSON
локальных виртуальных окружений
```

После этого:

``` bash
git commit -m "Initial commit: Kod Baikala AI"
```

Добавьте GitHub remote:

